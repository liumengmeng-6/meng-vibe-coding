# 筛选交互规范

## 什么时候用它

- 要给某个列表 / 表格加「筛选」（分类切换、只看某一类）
- 要检查一个已经做好的筛选功能合不合格

**不适用**：搜索框（那是"输入关键词过滤"，另一套规矩）、后端分页筛选。

## 规矩（写代码前先读，写完逐条自查）

### 1. 必须有「回到全部」这一档

只能筛进去、回不来，就是死路。
最少三档：`全部` / `分类 A` / `分类 B`。**「全部」不是可有可无的装饰，是出口。**

### 2. 三种状态都必须有交代

| 状态 | 要求 |
|---|---|
| 有结果 | 显示筛后的内容，并且**说清楚筛出了几条** |
| **没结果** | 必须有一句明确的话（例：「这个筛选下没有条目，点『全部』看看」）。**绝不允许白屏，也不允许只留一片空白** |
| 恢复 | 点「全部」回到筛选前的样子，一条不多、一条不少 |

> 第 2 条是最容易漏的。写代码的人总假设"用了筛选就一定有结果"，
> 但用户手上是真实数据 —— 总会有筛出 0 条的时候。**筛出 0 条却什么都不说，用户会以为页面坏了。**

### 3. 反馈要让用户看得见（不能只有颜色变了）

- 当前选中的那一档要「看起来就是选中了」——不能只靠颜色深浅，**要配合形状 / 边界 / 文字的变化**
  （色弱用户分不出深浅）
- 结果区要有**文字**变化：命中条数、空状态文案。
  **文字是最明确的一档反馈**（会一直留在那儿）；动效眨眼就过，只配当陪衬。

### 4. 键盘和读屏都要能用（可访问性）

- 筛选按钮必须是**真 `<button>`**（不是 `div` + `onclick`）——这样 Tab 能到、回车能触发，白捡
- 当前选中的档位要让读屏软件知道：给按钮加 `aria-pressed="true" / "false"`
- 把按钮们包进一个 `role="group"` + `aria-label`，读屏会说"筛选清单，分组，3 个按钮"
- 命中条数用一个 `aria-live="polite"` 的元素承载 —— 筛完读屏会自动播报新的条数
- 焦点样式**只写 `:focus-visible`**：鼠标点完不留一圈框，键盘操作才显示

### 5. 样式跟着项目走

- 颜色**只用 CSS 变量**，不写死色值
- `var()` **要带兜底值**（本项目约定：`var(--x, #默认)`）
- **明亮 / 赛博两套主题都要看得清**：正文对比度 ≥ 4.5:1，大字号 ≥ 3:1

## 自检怎么做

**不要靠肉眼。** 跑同目录的检查脚本：

```bash
node .workbuddy/skills/filter-interaction/scripts/check-filter.js
```

它会真的把页面加载起来、真的去点筛选按钮、逐项断言，然后打印 PASS / FAIL 清单，
并把这一次运行的结果写进 `LAST_RUN.md`。

> `LAST_RUN.md` 就是「这个 Skill 被真实调用过」的证据 ——
> 它是脚本的真实输出，不是手写的总结。

## 检查不通过怎么办

按 FAIL 那条的说明去改代码，改完重新跑，直到全过。

**不要把 FAIL 改写成「已知问题」就交差。** 检查清单要么全过，要么留一条明确的、写清原因的例外。
