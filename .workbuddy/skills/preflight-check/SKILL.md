# 发布前检查（preflight）

## 什么时候用它

- 要把项目**发布 / 部署 / 上线**之前
- 刚改完**主产品三件套**（`index.html` / `app.js` / `style.css`）或**云函数**，想确认没碰坏硬规矩
- 接手别人改过的代码，想快速知道"现在这份能不能上线"

**不适用**：查功能对不对（那是各自的专项检查，比如筛选功能用 `filter-interaction`）、
查排版好不好看、查文案通不通顺 —— 那些**机器判不了**，这里一概不查。

## 检查什么（六组）

| 组 | 查什么 | 对应项目硬规矩 |
|---|---|---|
| **A 断网可用** | 主产品有没有偷偷引 CDN / 外链脚本、有没有 `type="module"`、公网地址是否只在白名单里 | **AC14 / AC15** |
| **B 密钥** | 代码和文档里有没有"密钥长相"的字符串；`.env` / `*.pem` / `id_rsa` 有没有被提交进仓库 | 真钥匙不出门 |
| **C 双击即开** | 有没有 `charset` / `viewport`、有没有以 `/` 开头的绝对路径、`app.js` 里有没有 `fetch` 本地文件 | **AC1 / AC13** |
| **D 外链安全** | 每个 `target="_blank"` 的链接有没有带 `rel="noopener noreferrer"` | **AC22** |
| **E 后端跨域** | 三个云函数有没有把 CORS 改回通配 `*`、白名单内容是否一致、是否含线上域名 | Day 24 的成果别被改回去 |
| **F 仓库卫生** | 有没有误传 1MB 以上的大文件、`node_modules` 有没有进仓库 | 防手滑 |

> ⚠️ **范围说明**：A、C、D 只管**主产品三件套**（仓库根的那份）。
> `cloud/` 是后端探路区，它**本来就要联网**，不归 AC14 管 —— 别把两者混为一谈。

## 怎么跑

```bash
# ① 正常跑：检查当前项目，结果写进 LAST_RUN.md
node .workbuddy/skills/preflight-check/scripts/check-preflight.js

# ② 「故意弄坏」跑：验证它真的会报错，结果写进 LAST_RUN-demo.md
node .workbuddy/skills/preflight-check/scripts/check-preflight.js --demo
```

零依赖，不需要 `npm install`（只用 Node 自带的 `fs` / `path` / `child_process`）。

## 为什么要有一个 `--demo` 模式

**一个只会"全绿"的检查工具，等于没有。**

所以 `--demo` 会做这么一件事：把主产品三件套**复制一份到临时目录**，
往副本的 `index.html` 里**故意塞一行 CDN 外链脚本**（这是上线前最常犯的错），
再照常整套检查跑一遍。

- 副本从来没被真正部署过 —— **双保险：先证明它能报错，再用它检查真项目**
- 副本检查完就删，**不碰真文件一个字节**

如果你看到 `--demo` 也是全绿，那说明这个 Skill **坏了**（假通过），
它给出的任何"检查通过"都不能信。

## 检查不通过怎么办

按 FAIL 那条的说明去改，改完重跑，直到全过。

**不要把 FAIL 改写成「已知问题」就交差。**
要么修掉，要么在 `LAST_RUN.md` 里写清"这一条为什么可以放过"（极少数情况才有）。

**先判断一件事：这个 FAIL 是"真问题"还是"脚本跟不上变化了"。**

- 比如 A5 报"发现了 cdn."，先去看是不是只是某段**注释**里提到了 CDN 这个词 ——
  是的话，改脚本的关键字判定（别去删注释）；
- 比如 E4 报"白名单里没有线上域名"，先确认是不是**刚换了发布链接** ——
  是的话，去把三个云函数的白名单都补上，而不是改脚本。

## 记录下来

跑完会打印 PASS / FAIL 清单，并写下 `LAST_RUN.md`（`--demo` 写 `LAST_RUN-demo.md`）。

> `LAST_RUN.md` 就是「这个 Skill 被真实调用过」的证据 ——
> 它是脚本的真实输出，不是手写的总结。
