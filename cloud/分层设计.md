# 分层设计（Day 19）

> 这份文档回答一个问题：**「查数据库」的代码，从哪移到了哪？** 以及——为什么要这么移。

## 一句话

以前每个云函数的 `index.js` 里，**接口的事**和**数据库的事**混在一起；
Day 19 把**数据库的事**抽了出来，放进同目录的 `db.js`（数据访问层）。

```
「查数据库」这段代码：   index.js   ──搬到──▶   db.js
```

## 三层结构

```
┌──────────────────────────────────────────────────────────┐
│  浏览器 / 前端                                             │
│  打开  https://…/api/places?city=成都                      │
└───────────────────────────┬──────────────────────────────┘
                            │ HTTP
                            ▼
┌──────────────────────────────────────────────────────────┐
│  ① 接口层    functions/places/index.js                     │
│                                                            │
│  管"对外的样子"：                                           │
│    · 看请求是 GET 还是 POST，分流                           │
│    · 解析参数、做业务校验（缺 city 就报 400 中文）            │
│    · 拼查询条件（city_id=256 这样）                         │
│    · 把结果包成 { ok, data, error }                         │
│                                                            │
│  ✗ 不写 https、✗ 不认识网关地址                              │
└───────────────────────────┬──────────────────────────────┘
                            │  require('./db.js')
                            ▼
┌──────────────────────────────────────────────────────────┐
│  ② 数据访问层    functions/places/db.js                    │
│                                                            │
│  管"怎么跟数据库说话"：                                      │
│    · 环境 ID、钥匙（只从环境变量取）、超时                    │
│    ·  db.select(表, 查询串)      → 读                       │
│    ·  db.insert(表, 一行, 字段)   → 写                       │
│    · 把网关的错误整理成一句中文                               │
│                                                            │
│  ✗ 不认识"城市""地点"，✗ 不做业务校验                        │
└───────────────────────────┬──────────────────────────────┘
                            │ HTTPS
                            ▼
┌──────────────────────────────────────────────────────────┐
│  ③ 数据库    CloudBase PostgreSQL                          │
│    cities 表（370 城） / places 表（吃与玩）                 │
└──────────────────────────────────────────────────────────┘
```

## 一次请求怎么走（GET /api/places?city=成都）

| 步 | 在哪层 | 做了什么 |
|---|---|---|
| 1 | 接口层 | 收到请求，看到是 GET，取出 `city=成都` |
| 2 | 接口层 | 拼查询：`select=id,name&name=eq.成都&limit=1` |
| 3 | **数据访问层** | 带上钥匙，请求网关 `/v1/rdb/rest/cities?…` |
| 4 | **数据访问层** | 拿到响应，原样交回（**不判断对错**） |
| 5 | 接口层 | 判断：找到城市 → 拿 `city_id=256`，再查 places |
| 6 | **数据访问层** | 请求 `/v1/rdb/rest/places?city_id=eq.256&…` |
| 7 | 接口层 | 包成 `{ ok:true, data:[…], error:null }` 返回 |

**看第 3、4、6 步**：凡是要"出门上网"的地方，都在数据访问层里。

## 为什么这么拆

| | 拆之前 | 拆之后 |
|---|---|---|
| 想改"连接超时时间" | 每个 `index.js` 里各改一遍 | 只改 `db.js` |
| 想换网关地址 / 加个重试 | 在业务代码里翻半天 | `db.js` 一处 |
| 读 `index.js` 时 | 满屏 `https`、网关地址，干扰阅读 | 只剩"接口该干的事" |

## ⚠️ 两个 `db.js` 是重复的（这是故意的）

`cities/db.js` 和 `places/db.js` **内容一模一样**。为什么？

云函数之间是**彼此独立**的：每个函数部署时只打包自己目录下的文件，别人的文件它拿不到。
想让多个函数共用一份，要用控制台的「**层**」功能（把公共代码打进"层"、函数再绑定它）——
那是进阶玩法，本期不做。

所以：

- **这次拆分解决的是「职责分离」**（代码更好读、好改）
- **不是"消除重复"**（那要靠「层」）
- ⚠️ 因此：**改 `db.js` 时，两个函数里那份要一起改**，别让两边跑偏

## 文件对应

| 层 | 文件 |
|---|---|
| 接口层 + 业务 | `cities/index.js`、`places/index.js` |
| 数据访问层 | `cities/db.js`、`places/db.js`（两份相同） |
| 不涉及数据库 | `health/index.js`（它谁都不查，只回"我还活着"） |
