## 四个接口（Day 17–18 已全部上线）

> **完整契约（请求参数 / 字段说明 / 各种失败情况）在 `api-contract.md` 第三～五节（POST 见「五之二」）。**
> 这里只是一张"找得到路"的速查表。

| 接口 | 地址 | 需要什么 | 返回什么 |
|---|---|---|---|
| **健康检查** | `…/api/health` | 什么都不用 | `{ok, service, message, time, uptimeSeconds}` |
| **城市白名单** | `…/api/cities` | 什么都不用 | `data` = 370 个 `{id, name, created_at}` |
| **美食美景清单** | `…/api/places?city=成都` | **`city` 必填**（城市名） | `data` = 该城的地点数组 |
| **新增地点** | `…/api/places`（POST） | JSON：`city`+`name`+`type` 必填 | `201` + `data` = 新增那一行 |

四个接口的**完整前缀**都是：

```
https://travel-planner-d4g8o6mee9d231c64.service.tcloudbase.com
```

### 统一的返回形状（前端只认这一种）

```json
成功：{ "ok": true,  "data": [...], "error": null }
失败：{ "ok": false, "data": null,  "error": "人能看懂的中文说明" }
```

> ⚠️ **三个字段永远都在** —— 成功时 `error` 是 `null`、失败时 `data` 是 `null`。
> 前端不用先判断"字段存不存在"，写法简单一半。

**两条要记住的细节**（都写在契约第二节「例外」里）：

| 细节 | 说明 |
|---|---|
| **字段名是下划线风格** | `city_id`、`created_at` —— 跟数据库列名一样，**不是** `cityId`。用户拍板选的这条 |
| **`created_at` 末尾没有 `Z`** | 数据库 `timestamp` 原样出来，**不要**当成标准 UTC 时间用 |

### 试一下（浏览器地址栏直接粘）

```
https://travel-planner-d4g8o6mee9d231c64.service.tcloudbase.com/api/cities
```

```

```

**能看到 JSON 就是通的。** 地址栏 / `curl` 不受跨域限制，是排查问题的第一选择。

### 真库验证（Day 17 做过一次，方法可复用）

想证明"接口读的是真数据库、不是写死的"，就做这个对照：

1. 记下 `…/api/places?city=成都` 里「宽窄巷子」的 `price`（当时是 `0`）
2. SQL 编辑器跑 `UPDATE places SET price = 1 WHERE name = '宽窄巷子';`
3. `Ctrl + Shift + R` **强制刷新**接口地址 → `price` 变成 `1`
4. 改回 `0`

> **第 3 步一定要强制刷新** —— 普通刷新可能读到浏览器缓存，你会以为"没变"。

## 数据库：两张表（Day 16 建）

### 用的哪种数据库

CloudBase 的 **「SQL 型数据库」→ PostgreSQL**。

⚠️ 两个容易踩的点：

1. 控制台里**默认**那个「数据库」是**文档型**的 —— 它存 JSON、叫"集合"不叫"表"、**没有字段类型、也没有 SQL**。本项目要的是**另一个入口**：左侧菜单里的「SQL 型数据库」。
2. 这个环境里的 SQL 数据库是 **PostgreSQL，不是 MySQL**。两者都叫 SQL，但写法不一样 —— `db/` 下两个脚本**是按 PostgreSQL 写的**，直接拿去 MySQL 跑不了。

### 两张表分别存什么

| 表 | 一行是什么 | 行数 | 数据来源 |
|---|---|---|---|
| `cities` | 一个**程序认不认**的城市 | **370** | `app.js` 的 `CN_CITIES` |
| `places` | 某城市的一条**吃 / 玩**项目 + 参考价 | **12**（成都 6 + 重庆 6） | `app.js` 的 `CITY_HIGHLIGHTS` |

### 关联：`places.city_id` → `cities.id`

地点表里**不写"成都"两个字，只写数字**；想知道这个数字是谁，去 `cities` 表里按它找。

| | 实际情况 |
|---|---|
| `cities` 里 | `id=4` → 重庆；`id=256` → 成都 |
| `places` 里 | 成都那 6 条地点的 `city_id` 全是 `256`；重庆那 6 条全是 `4` |

一个城市对多条地点，这叫**一对多**。

**为什么不把城市名直接存在 `places` 里**：城市改名时只需改 `cities` 一处，地点表不用动。
代价是查的时候要多一次 join。**这个字段就是"两张表靠哪个字段关联"的答案。**

### 怎么重建（万一表丢了）

在控制台的 **SQL 编辑器**里**按顺序**执行这两份：

| 顺序 | 文件 | 干什么 | 能重复执行吗 |
|---|---|---|---|
| ① | `db/schema.sql` | 建两张空表（字段 / 约束 / 注释） | ✅ 表已在就跳过 |
| ② | `db/seed.sql` | 灌 370 + 12 行数据 | ✅ 见下表 |

**顺序不能反** —— `places` 有一个外键指着 `cities`，城市表不在会直接报错。

**重复执行时两张表的行为不一样（这是故意设计的）**：

| 表 | 第二遍跑会发生什么 | 为什么 |
|---|---|---|
| `cities` | **什么都不做** | 除了城市名没有别的可更新字段 |
| `places` | **刷新** `type` / `price` / `note` | 以后改了 `app.js` 里的价格，重跑一遍就同步了 |

> ⚠️ 它只管"改"和"加"，**不管"删"** —— 你在 `app.js` 里删掉一条地点，库里那行**不会自己消失**，得手动删。

> 💡 **执行小提示**：SQL 编辑器默认**只执行光标所在的那一条语句**。粘完脚本后先 `Ctrl + A` 全选、再点执行，否则可能只跑了一句 —— 这个坑真踩过。

### 数据不是手抄的

370 个城市手抄必错，所以 `db/seed.sql` 是**脚本从 `app.js` 里原样抽出来**的。

改动流向是这样一条链：

```
app.js 里的 CN_CITIES / CITY_HIGHLIGHTS
      ↓  跑一次生成脚本
    db/seed.sql
      ↓  在控制台 SQL 编辑器里执行
   云上两张表
```

**所以改完 `app.js` 里的数据，要重跑一遍这条链，云上才跟得上**（见下一节）。

## 常见担心：开始学后端以后，改前端会不会变麻烦？

> **不会。** 这条分隔**恰好就是为了保护这件事**才做的。
> 下面把"为什么不麻烦"讲清楚，以后心里有底。

### 为什么改前端不会牵连后端

后端代码**跑在腾讯云上**，前端代码**在你电脑上**。你在 `app.js` 里改多少行，
云上那个函数**一个字节都不会变**。

| 你想改的东西 | 会不会牵连后端 |
|---|---|
| 页面好不好看、字体、配色、动效 | ❌ 完全不牵连 |
| 加个视图、改表格排版 | ❌ 完全不牵连 |
| **改算钱的规则、改行程分配逻辑** | ❌ 完全不牵连（算钱永远在浏览器本地） |
| 加一个**纯前端**功能 | ❌ 完全不牵连 |

### 唯一会变麻烦的情况

**如果你改前端时，"顺手"让它去调后端接口** —— 比如看着 `GET /api/places` 好用，
就想让主产品的美食清单从云上拉。

那一瞬间，麻烦**不是来自后端，是来自丢掉了 `AC14`（断网可用）**：

```
现在（安全）：  改前端 ←→ 后端    两块地中间有墙，互相改不动对方
踩线之后（麻烦）：改前端 → 必须考虑"后端挂了怎么办""没网怎么办""数据格式对不上怎么办"
```

### 三种改法，对照着看

| 你想做的改动 | 麻不麻烦 | 要做什么 |
|---|---|---|
| **纯外观 / 纯交互** | 🟢 不麻烦 | 只改 `app.js` / `style.css`，跟平时一样 |
| **改算钱、改行程逻辑** | 🟢 不麻烦 | 同上（这也是为什么第 3 周**不做** `POST /api/plan` —— 就是为了保住这份自由） |
| **让主产品用云上数据** | 🟡 要先想清楚 | **必须先改 `PRD.md`**（正式改 `AC14` 口径、说明为什么放弃离线），**不能悄悄加一行 `fetch`** |

> **换句话说**：只有你**主动选择**"我要让主产品联网"时才要走流程。
> 其他时候，**后端的进度完全不会拖住你**。

### 一件要记得同步的小事

这份数据现在**有两处**：一处在 `app.js` 里（内置），一处在云上数据库里（Day 16 建的）。

| | 谁是权威 | 为什么 |
|---|---|---|
| 城市清单 / 美食美景清单 | **`app.js`** | 主产品断网也要能用（`AC14`）；云上那份只是"给以后的接口预备的副本" |

**所以规矩是**：改数据时**改 `app.js`**，然后重跑生成脚本 + 重跑 `seed.sql`，让云上跟上
（步骤见上面「数据库」一节的「怎么重建」）。

**反过来不用做**：云上那份改了，不会影响主产品 —— 这就是两块地分着的意义。

### 一句话

> **主产品不调后端任何接口；`cloud/` 不进主产品的计算链。**
>
> 只要这条线不破，**你以后想怎么改前端都行**。
