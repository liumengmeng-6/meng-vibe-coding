## 一、为什么要有"契约"这个东西（先讲清楚）

前后端是两个**互不相识**的零件。前端只管"我要问什么"，后端只管"我能答什么"。

**如果不定契约会怎样**：

| 前端以为 | 后端实际给 | 结果 |
|---|---|---|
| 字段叫 `data` | 字段叫 `result` | 前端读 `undefined`，看着像"没数据"，其实是名字对不上 |
| 一定返回数组 | 出错时返回了 `{error: ...}` | 前端按数组遍历，直接崩 |
| 时间格式是 `"10:00"` | 给的是时间戳 `1727760000` | 页面上显示一串数字 |

**契约就是把这三件事提前说死**：① 地址叫什么 ② 发什么过去 ③ 收什么回来（**包括出错时收什么**）。

> ⚠️ **最容易漏的是第 ③ 条里的"出错时"**。只写"成功怎么返回"的契约是残缺的 ——
> 因为**出错一定会发生**（断网、超时、参数错）。不提前说好，前端就只能瞎猜。

## 二、通用约定（所有接口都遵守）

| 项目 | 约定 | 为什么 |
|---|---|---|
| **协议** | HTTPS | 浏览器在 HTTPS 页面里不允许调 HTTP 接口 |
| **数据格式** | JSON（`Content-Type: application/json; charset=utf-8`） | 统一；`charset=utf-8` 是为了中文不乱码 |
| **字符编码** | UTF-8 | 同上 |
| **时间格式** | **ISO 8601 字符串**，如 `"2026-10-01T14:46:30.000Z"` | 无歧义、带时区、JS 能直接 `new Date()` 解析 |
| **成功判据** | HTTP 状态码 `200` **且** 返回体里 `ok === true` | 双保险：网络层和业务层都确认 |
| **失败判据** | HTTP 状态码非 200，**或** `ok === false` | 同上 |

### 命名风格

- **一律小驼峰**：`uptimeSeconds`（不是 `uptime_seconds`）
- **布尔值用 `is` / `has` / `ok` 开头或本身就是形容词**：`ok`、`isReturn`
- **时间字段以 `time` / `At` 结尾**：`time`、`createdAt`

> 命名一致比"取个好名字"更重要 —— 它让代码读起来没有意外。

### ⚠️ 例外一：数据类接口的字段名「沿用数据库」（Day 17 加）

上面那句「一律小驼峰」**管的是我们自己定的字段**（比如 `ok`、`service`、`time`）。
**但"把数据库里的记录原样吐出来"的那类接口是例外** ——
`/api/cities`、`/api/places` 返回的字段名**跟数据库表的列名一模一样**，是**下划线风格**：

| 接口 | 字段名 |
|---|---|
| `/api/cities` | `id`、`name`、`created_at` |
| `/api/places` | `id`、`city_id`、`name`、`type`、`price`、`note`、`created_at` |

**为什么开这个例外**：

| 理由 | 说明 |
|---|---|
| **一眼对得上** | 排查时，接口给的 `city_id` 和你在 SQL 编辑器里 `SELECT` 出来的列名**是同一个字**，不用心算翻译 |
| **少一层手写错** | 每个字段都手动改名，字段一多就是一处改错的机会（将来加字段时尤其容易漏） |
| **不假装** | 这就是数据库真实的样子，如实反映反而更好排查 |

**代价（必须记住）**：读这两个接口的数据时，要写 **`p.city_id`**，不是 `p.cityId`。
**别照上面那句"一律小驼峰"去猜 —— 数据类接口一律以下面的字段表为准。**

> 这条是 **Day 17 由用户拍板定的**（当时两个选择：**改契约** / 改代码；选的是**改契约**）。

### ⚠️ 例外二：时间字段不带时区后缀（Day 17 加）

第二章写的时间格式是 **ISO 8601 带时区**（末尾有 `Z`）。但数据类接口的时间
是从数据库 `timestamp` 列直接出来的，**长这样**：

```
"created_at": "2026-10-03T16:03:38.079692"
```

跟标准的差别有两点，**别当成 bug**：

| 差别 | 说明 |
|---|---|
| **末尾没有 `Z`** | 数据库这个列存的是**不带时区**的时间，不是标记过 UTC 的时刻，所以序列化出来也没带 `Z` |
| **小数位是 6 位** | 数据库精度到微秒（`.079692`），不是毫秒的 3 位 |

**前端怎么用**：`created_at` 现阶段**只用于排查**，不参与任何计算和显示。
将来真要显示时间，**必须先明确"这个时间是哪个时区"** —— 现在没定，所以先不显示。

> ⚠️ **我们自己定义的时间字段不受影响** —— `/api/health` 的 `time` 仍然带 `Z`。两条别混。

## 三、接口 ①：`GET /api/health`（后端连通性检查）

### 它是干什么的

**回答一个问题：「后端现在还活着吗？」**

前端调用它，如果能拿回 JSON，就说明这条链路是通的：

```
浏览器  →  HTTPS  →  云函数  →  返回 JSON  →  浏览器
```

**它不读数据库、不调外部服务、不需要登录。** 故意做成最简单的，这样一旦出问题，只可能是「部署 / 权限 / 域名」的问题，不会掺进业务逻辑的干扰。

### 请求

| 项目 | 值 |
|---|---|
| **方法** | `GET` |
| **路径** | `/api/health` |
| **完整地址** | `https://{你的环境地址}/api/health` |
| **是否鉴权** | ❌ 不需要 |
| **请求参数** | 无 |
| **请求体** | 无 |

### 成功响应（HTTP 200）

```json
{
  "ok": true,
  "service": "travel-planner-health",
  "message": "后端连通了",
  "time": "2026-10-01T14:46:30.000Z",
  "uptimeSeconds": 128
}
```

### 字段说明

| 字段 | 类型 | 一定有？ | 含义 | 备注 |
|---|---|---|---|---|
| `ok` | boolean | ✅ | 服务是否正常 | **固定为 `true`** —— 能返回就代表健康 |
| `service` | string | ✅ | 服务名 | 固定 `"travel-planner-health"`，用于确认"调对地方了" |
| `message` | string | ✅ | 给人看的一句话 | 可直接显示在页面上 |
| `time` | string | ✅ | 服务器当前时间 | ISO 8601 格式 |
| `uptimeSeconds` | number | ✅ | 函数已运行秒数 | 整数，四舍五入到秒 |

> **为什么要有 `time`**：它每次调用都不同。这样你看到的结果**一定是最新的一次**，
> 而不是浏览器把旧缓存给了你。**没有这个字段，你分不清"真通了"和"看到的是旧的"。**

### 失败响应

| 情况 | HTTP 状态码 | 返回体 | 前端应怎么处理 |
|---|---|---|---|
| 路径写错 | `404` | 平台默认错误页（**不是**我们的 JSON） | 提示"地址不对，检查是否漏了 `/api/health`" |
| 云函数没部署 / 没开 HTTP 访问 | `404` | 同上 | 提示"后端还没部署好" |
| 云函数内部报错 | `500` | 平台默认错误信息 | 提示"后端出错了"，并展示原文 |
| 跨域被拦 | — | **浏览器直接拦，前端拿不到响应** | 提示"跨域被拦"，指向本文第六节 |
| 断网 / 地址解析不了 | — | `fetch` 抛异常 | 提示"请求失败"，展示异常信息 |

> ⚠️ **注意上表里"404"的两行**：**平台自己的 404 页不是我们的 JSON**。
> 所以前端**不能只看状态码**，还要试着解析返回体 —— 解析不出 JSON，
> 就说明**根本没打到我们的函数**，而不是"函数说找不到"。这两件事的排查方向完全不同。

### 调用示例

**浏览器地址栏**：直接把完整地址粘进去回车，应该看到 JSON。

**命令行**：
```bash
curl https://{你的环境地址}/api/health
```

**前端 JS**：
```js
const res = await fetch('https://{你的环境地址}/api/health');
const data = await res.json();
console.log(data.ok, data.message);
```

## 四、接口 ②：`GET /api/cities`（城市白名单）

### 它是干什么的

**回答一个问题：「这个城市，程序认不认？」**

主产品现在靠浏览器里内置的一张 370 城白名单判断（`app.js` 的 `CN_CITIES`）。
这个接口把**同一份白名单搬到云上**，让"白名单可以随时改、不用重新发版"成为可能。

**它只读数据库、不改数据、不需要登录。**

### 请求

| 项目 | 值 |
|---|---|
| **方法** | `GET` |
| **路径** | `/api/cities` |
| **完整地址** | `https://travel-planner-d4g8o6mee9d231c64.service.tcloudbase.com/api/cities` |
| **是否鉴权** | ❌ 不需要（网关路由的「身份认证」已关闭） |
| **请求参数** | 无 |
| **请求体** | 无 |

### 成功响应（HTTP 200）

```json
{
  "ok": true,
  "data": [
    { "id": 1, "name": "北京", "created_at": "2026-10-03T16:03:38.079692" },
    { "id": 2, "name": "上海", "created_at": "2026-10-03T16:03:38.079692" }
  ],
  "error": null
}
```

**实测（Day 17 复核）**：HTTP `200`、`ok:true`、**`data.length = 370`**，
字段名正好是 `id, name, created_at`。

### 字段说明

| 字段 | 类型 | 一定有？ | 含义 |
|---|---|---|---|
| `ok` | boolean | ✅ | 成功固定 `true` |
| `data` | array | ✅ | 城市数组；**失败时固定为 `null`** |
| `error` | string \| null | ✅ | 成功固定 `null`；失败时是**中文说明** |

> ⚠️ **三个字段永远都在** —— 成功时 `error` 是 `null`、失败时 `data` 是 `null`。
> 前端不用先判断"这个字段存不存在"，写法简单一半。

`data` 里每一项：

| 字段 | 类型 | 含义 | 备注 |
|---|---|---|---|
| `id` | number | 城市在库里的编号 | 主键；`places.city_id` 指的就是它 |
| `name` | string | 城市名（如 `"成都"`） | 唯一，不会重复 |
| `created_at` | string | 这行数据入库时间 | ⚠️ 见第二节「例外二」 |

> **`id` 不要当成"城市排序"或"城市代码"用** —— 它只是数据库的流水号。
> 成都的 `id` 是 **256**、重庆是 **4**，顺序看着乱是正常的。

### 失败响应

| 情况 | HTTP 状态码 | `error` 里的话（大意） | 前端应怎么处理 |
|---|---|---|---|
| 云函数没配数据库钥匙 | `500` | 云函数还没配数据库钥匙。请到「云函数 → cities → 配置 → 环境变量」加一条：… | 部署问题，提示"后端还没配好" |
| 数据库网关拒绝（钥匙错） | `502` | 数据库网关返回了 401。原文（截断）：… | **退回浏览器内置的 370 城** |
| 连不上 / 超时 | `502` | 连不上数据库网关：… | 同上 |
| 网关回的不是数组 | `502` | 返回的不是数组（预期是城市列表）… | 同上 |
| 用了 POST 等非 GET 方法 | `405` | 这个接口只支持 GET（只看数据，不改数据）… | 代码写错了 |
| 路径拼错 | `404` | 平台默认页（**不是**我们的 JSON） | 提示"地址不对" |

> ⚠️ **"读不到就退回内置那份"是硬规矩**（见第七节末尾那条铁律）。
> 接口失败**不能**让页面变成"用不了"，只能让它"少了一点云端的增强"。
>
> ⚠️ 还有一条：**`404` 时返回的可能是平台自己的页面、不是我们的 JSON** ——
> 前端不能只看状态码，还要试着解析返回体（同第三节那条提醒）。

### 调用示例

```bash
curl https://travel-planner-d4g8o6mee9d231c64.service.tcloudbase.com/api/cities
```

```js
const res = await fetch('https://travel-planner-d4g8o6mee9d231c64.service.tcloudbase.com/api/cities');
const { ok, data, error } = await res.json();
if (ok) console.log(data.length); // 370
```

## 五、接口 ③：`GET /api/places?city={城市名}`（某城的美食美景清单）

### 它是干什么的

**回答一个问题：「这个城市有什么吃的玩的、大概多少钱？」**

主产品现在内置了成都、重庆两套清单（`app.js` 的 `CITY_HIGHLIGHTS`）。
这个接口把清单搬到云上 —— **将来加城市不用改前端代码**。

### 请求

| 项目 | 值 |
|---|---|
| **方法** | `GET` |
| **路径** | `/api/places` |
| **查询参数** | **`city`（必填）** —— 城市名，**中文，要 URL 编码** |
| **是否鉴权** | ❌ 不需要 |
| **请求体** | 无 |

**完整地址**（`成都` 编码后是 `%E6%88%90%E9%83%BD`；浏览器地址栏里直接写中文也能用）：

```
https://travel-planner-d4g8o6mee9d231c64.service.tcloudbase.com/api/places?city=成都
```

### 成功响应（HTTP 200）

```json
{
  "ok": true,
  "data": [
    { "id": 1, "city_id": 256, "name": "龙抄手（总店）", "type": "en", "price": 20, "note": "一碗抄手，人均约 20 元", "created_at": "…" },
    { "id": 4, "city_id": 256, "name": "大熊猫繁育研究基地", "type": "play", "price": 55, "note": "学生票约 27 元，记得带学生证", "created_at": "…" }
  ],
  "error": null
}
```

**实测（Day 17 复核）**：

| 请求 | 结果 |
|---|---|
| `?city=成都` | `200` / 6 条，`city_id` 全是 **256** |
| `?city=重庆` | `200` / 6 条，`city_id` 全是 **4** |

### 字段说明

外层 `ok` / `data` / `error` 同接口 ②。`data` 里每一项：

| 字段 | 类型 | 含义 | 取值 |
|---|---|---|---|
| `id` | number | 地点编号 | 主键 |
| `city_id` | number | **属于哪个城市** —— 指向 `cities.id` | 成都 `256`、重庆 `4` |
| `name` | string | 地点名 | 同一城市内不重复 |
| `type` | string | 类型 | **只有两个值**：`"en"`（吃）/ `"play"`（玩） |
| `price` | number | 参考价（元），整数 | 免费是 `0` |
| `note` | string | 一句话说明 | 可能是空串 |
| `created_at` | string | 入库时间 | ⚠️ 见第二节「例外二」 |

> **`type` 为什么不写成 `eat`**：主产品代码里用的就是 `"en"`（吃）和 `"play"`（玩），
> 这里跟它保持一致，**免得前端还要做一次翻译**。

> **`price` 的性质**：这是**参考价 / 人均估算**，不是实时票价（见 `PRD.md`）。
> **页面上显示时必须带「估算值，仅供参考」**（AGENTS.md 8.7-4）。

### 失败响应

| 情况 | HTTP 状态码 | `error` 里的话（大意） | 前端应怎么处理 |
|---|---|---|---|
| **没传 `city`** | `400` | 请指定城市，例如：/api/places?city=成都。可用城市见 GET /api/cities | 代码写错了，提示一下即可 |
| **城市不存在** | `404` | 没有找到城市「XX」。可用城市见 GET /api/cities | **退回内置清单** |
| 该城暂时没有地点 | `200` | ——（算成功，但 `data` 是**空数组** `[]`） | ⚠️ **显示"这个城市暂时没有清单"，不能一片空白** |
| 数据库故障 | `502` | 同接口 ② | 退回内置清单 |
| 非 GET 方法 | `405` | 这个接口只支持 GET… | 代码写错了 |

> ⚠️ **注意「城市不存在（404）」和「城市没地点（200 + `[]`）」是两件事**：
> 前者是"库里没这个城市"，后者是"有这个城市、只是还没录地点"。**前端要分开处理。**

### 它内部做了什么（了解即可）

一次调用里其实**查了两次库**：

```
① 按 city 名去 cities 表查 → 拿到 id（成都 → 256）
② 按 city_id = 256 去 places 表查 → 拿到那 6 条
```

**为什么要绕这一步**：因为 `places` 里存的是数字 `256`，不是"成都"两个字
（这就是 Day 16 说的「两张表靠 `city_id` 关联」）。
多一次查询换来的是**城市改名不影响地点表**。

### 调用示例

```bash
curl "https://travel-planner-d4g8o6mee9d231c64.service.tcloudbase.com/api/places?city=%E6%88%90%E9%83%BD"
```

```js
const url = 'https://travel-planner-d4g8o6mee9d231c64.service.tcloudbase.com/api/places?city='
          + encodeURIComponent('成都');
const res = await fetch(url);
```

> **⚠️ `encodeURIComponent` 不能省** —— 中文直接拼进网址，有些环境会出错。

## 五之二、接口 ④：`POST /api/places`（新增用户自填地点，Day 18）

### 它是干什么的

让用户往美食美景清单里**添加一条自己的地点**（页面上「自己添加地点」那个动作，见第七节第 9 行）。
写进去之后，`GET /api/places?city=同城市` 就能读到它 —— **写入 + 读回 = 闭环**。

### 写哪张表（Day 18 拍板）

**现有 `places` 表**，**不**单开 `user_places` 表。

### 请求

```
POST https://travel-planner-d4g8o6mee9d231c64.service.tcloudbase.com/api/places
Content-Type: application/json
```

```json
{ "city": "成都", "name": "锦里", "type": "en", "price": 30, "note": "小吃街，参考价" }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `city` | ✅ | 城市名（**不是** `city_id`）—— 必须是 `cities` 表里有的，否则 404 |
| `name` | ✅ | 地点名，最长 64 字 |
| `type` | ✅ | 只能 `"en"`（吃）或 `"play"`（玩）—— 与数据库 CHECK 一致 |
| `price` | ❌ | 非负整数（元）。不填按 `0` 算。数字字符串 `"30"` 也收（宽容处理） |
| `note` | ❌ | 一句提示，最长 255 字。不填按空字符串算 |

### 成功响应（HTTP 201）

```json
{
  "ok": true,
  "data": {
    "id": 61,
    "city_id": 256,
    "name": "锦里",
    "type": "en",
    "price": 30,
    "note": "小吃街，参考价",
    "created_at": "2026-10-07T08:59:30.478744"
  },
  "error": null
}
```

> 字段名沿用数据库下划线风格（`city_id` / `created_at`，见第二节例外）；
> `created_at` 不带时区后缀 `Z`（同例外）—— 实测格式是 `2026-10-07T08:59:30.478744`（**`T` 分隔 + 6 位微秒**）。
>
> ⚠️ **`id` 不连续是正常的**（实测第一天写入拿到的是 `61`，不是 `13`）：
> 种子脚本 `seed.sql` 用的是 `ON CONFLICT DO UPDATE`，PostgreSQL 每次尝试插入都会**先消耗**一个自增号，
> 冲突了就回滚数据但**号码不退**。反复重跑 seed 会把序号推高。**判断"有没有多一行"要看行数，不要看 id。**
> **`data` 就是库里新增的那一行。**

### 失败响应

| 情况 | HTTP | `error` 说什么（示例） | 前端怎么办 |
|---|---|---|---|
| 请求体不是 JSON 对象 | `400` | 请求体不是能认的 JSON 对象。请用 Content-Type: application/json… | 检查请求写法 |
| 缺 `city` / `name` / `type` 任一必填 | `400` | **缺少必填字段 name（地点名）**…… | 提示用户补字段 |
| `type` 不是 en/play | `400` | type 的值不对：收到的是 "food"。只能填 "en"（吃）或 "play"（玩） | 提示重选 |
| `price` 不是非负整数 | `400` | price 必须是 0 或正整数（元）。收到的是 "-5"。 | 提示改价 |
| `name` 超 64 字 / `note` 超 255 字 | `400` | name 太长了（65 个字，上限 64）…… | 提示缩短 |
| 城市不存在 | `404` | 没有找到城市「东京」，添加不了。可用城市见 GET /api/cities | 提示换城市 |
| **同城市同名已存在（重复提交）** | `409` | 「锦里」在「成都」已经存在（第 61 条，吃，参考价 30 元），不要重复添加。 | **明确告诉用户已存在** |
| 数据库故障 | `502` | 写入时数据库网关返回了 … | 退回 localStorage |

> **防重复是两层保险**：第 1 层函数先查（返回上面那条人话）；第 2 层数据库
> `UNIQUE(city_id, name)` 兜底 —— 撞上约束时函数把它**翻译成同样的中文**再返回，不让用户看到英文报错。

### 它内部做了什么（了解即可）

```
① 校验请求体（纯函数，缺什么说什么）
② cities 表按名字查 id（成都 → 256）—— 和 GET 同款两步走
③ places 表按 city_id + name 查重 → 已存在就 409
④ 插入 places（Prefer: return=representation，让库把新行原样还回来）
⑤ 201 + 新行
```

## 六、跨域（CORS）—— Day 17 已配

**什么叫跨域**：浏览器的安全规则 —— **一个网页只能随便读"同源"的响应**。
如果网页在 `a.com`、接口在 `b.com`，浏览器会**先拦下来**，除非接口明确说"我允许 `a.com` 读"。

**现在的状态（Day 17 配，Day 18 扩）**：两层都已经打开。

| 在哪一层 | 怎么配的 |
|---|---|
| **网关路由** | HTTP 网关里那条路由的「**跨域设置**」= **开** |
| **云函数代码** | 每个函数都带 `Access-Control-Allow-Origin: *`，并且**答应浏览器的 `OPTIONS` 预检**（回 `204`）；**Day 18 起 `places` 函数的方法列表加了 `POST`** |

> **为什么两层都要**：预检（`OPTIONS`）是浏览器在正式请求**之前**自己发的 ——
> 函数不答应它，正式请求根本发不出去。所以只配网关不够，**函数也得回**。

> **`*` 是什么意思**：允许**任何**来源的网页读这个接口。**Day 18 起接口能写数据了，但仍保持 `*`** ——
> 理由：① 没有账号体系，写的是公共清单数据、不是隐私；② `curl` 调试不受跨域限制，先保调试顺畅。
> **「收紧到只允许自己的域名」记入待办，在接入真实用户数据之前完成。**
